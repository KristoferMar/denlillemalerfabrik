# Hoverkomponent: vis farver i tilfældig rækkefølge i stedet for slavisk lys→mørk

Airtable record: `rec2RfcHl5R7Wn8RL` (Den Lille Malerfabrik, Priority **P2**, Order 10)

> **Title (verbatim):** "I vores hoverkomponent som ligger på forsiden skal vi have gjort således så komponentet viser \"random\" farver frem for at vi ser nuancer i slavisk rækkefælge."

## Component identified

The "hoverkomponent" on the homepage is the **`kmeconsulting-product-finder`** section
(`sections/kmeconsulting-product-finder.liquid`, registered in `templates/index.json`
as `kmeconsulting_product_finder`, second section after the hero). Its heading reads
*"Hold musen over en farve. Klik for at se den i et rum."* — i.e. the hover-over-color
component the todo is describing.

Today, the section renders the 200-color palette as an 8-column × 25-row CSS grid
(8 families × 25 tonal shades). Each column = a family; each row within a column =
a tonal step from lightest (top) to darkest (bottom), ordered by `dlm_code`. That's
the "slavisk rækkefølge" the todo wants to break up.

## Approach

- **Client-side shuffle in `assets/kmeconsulting-product-finder.js`**, on init, before the
  family-filter handlers attach. Shopify Liquid has no `shuffle` filter, and the
  source data is auto-generated by `scripts/sync-colors-to-shopify.mjs` into
  `snippets/paint-colors-data.liquid` — a JS-only change keeps the existing
  server-rendered grid structure intact.
- **Permute visual content, not DOM nodes.** For each family group (8 of them), collect
  the swatches with `data-family="X"` that are NOT `--empty`, Fisher-Yates shuffle
  the **non-anchor** subset (rows 4–24), then swap the visible attributes in place:
  `data-color-name`, `data-color-code`, `data-color-hex`, `aria-label`, the chip
  background-color inline style, and the `.vores-farver__swatch-name` /
  `.vores-farver__swatch-code` text. DOM order, grid layout, and CSS-grid cell
  assignments stay untouched — so the family-column visual structure, the family
  filter pills, the collapsed/anchor view, and the click→inspiration-photo
  lookup (keyed off `data-color-code` / `data-color-hex`) keep working unchanged.
- **Preserve anchors (rows 0–3).** The collapsed default view shows only the first 4
  rows = 32 anchor shades — the curated "headline" colors per family. The complaint
  is the strict light→dark gradient in the **expanded** view (rows 4–24, the 21
  tonal expansions added 2026-05-12). Anchors stay in their curated positions;
  the 21 tonal expansions per family get scrambled. This also keeps the "Vis flere
  farver" UX coherent: the collapsed-state first impression is unchanged, only the
  expansion looks scattered.
- **Fresh shuffle per page load** (no seeded RNG). The todo puts "random" in quotes
  and the goal is purely visual — a per-load Fisher-Yates is the simplest delivery.
  Repeat-visitor consistency isn't a concern for this section (no deep linking by
  position; all lookups are by `data-color-code`).

## Files likely to change

- `assets/kmeconsulting-product-finder.js` — add a `shuffleNonAnchorSwatches()`
  function inside the existing IIFE (verified to exist; the IIFE already starts at
  line 1 and resolves `grid` from `#vores-farver-grid`). Call it once at init,
  before the family-filter and "Vis flere farver" handlers attach.

No other files. No Liquid changes. No CSS changes. No changes to
`snippets/paint-colors-data.liquid` or `scripts/sync-colors-to-shopify.mjs` —
the source-of-truth ordering (light→dark by `dlm_code`) is preserved on the
server side, the scramble is purely a presentation-layer effect.

## Risks / open questions

- **Visual: row N of column X no longer numerically increases.** After the shuffle,
  the small `DLM####` code shown under each swatch in the expanded view will no
  longer be in ascending order within a column. This is the desired effect (it's
  literally what the todo asks for) — flagging in case the user wants to also
  hide the code label in the expanded rows.
- **Filter pills.** Clicking a family pill currently hides non-matching swatches;
  the visible ones reflow in DOM order, which becomes scrambled-but-anchored-first
  (anchors at top, expansions scrambled below). Acceptable per the same reasoning
  as the global view.
- **Empty placeholders.** All 8 families currently have 25 entries each, so no
  `--empty` placeholders are rendered today. The shuffle code will still filter
  `[data-empty="true"]` out of the pool defensively in case a future family
  comes in short.
- **Accessibility.** The `aria-label` on each swatch is swapped along with the
  other content attributes, so screen readers announce the correct color name+code
  for whichever shade ends up in a given cell.
- **Open question (non-blocking):** Should the "Vis flere farver" expand action
  re-shuffle the expanded swatches? Current plan: no — one shuffle per page load
  to keep behavior consistent within a single session. Easy to revisit.
